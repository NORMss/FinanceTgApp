# Этап 0. Ресерч и выбор стека

Дата: 2026-08-11
Контекст: Telegram Mini App для семейных финансов на 2 человек, минимальный VPS, Docker, расширяемость.

---

## 1. Что уже есть на рынке

Почти всё, что находится по запросу «telegram + finance + google sheets» — это **боты, а не Mini Apps**. Готового
open-source Mini App с Google Sheets в качестве хранилища фактически нет, так что мы собираем свой, но можем
забрать удачные решения:

| Проект | Что полезно забрать |
|---|---|
| [telexpense](https://github.com/pavelmakis/telexpense) | Service account + шаблон таблицы, который пользователь копирует себе и шарит боту. Вкладки `Transactions` / `Accounts` / `Categories`. Бот сам не хранит финансы. |
| [microw](https://github.com/sickmz/microw) | Локальный xlsx как основное хранилище + синхронизация в Sheets. Бюджеты с алертами, графики. |
| [finance-tracker-bot](https://github.com/edoardob90/finance-tracker-bot) | OAuth2 вместо service account (таблица остаётся в аккаунте пользователя), локальный буфер записей. |
| [Expense-Tracker-Bot](https://github.com/KotsanTW/Expense-Tracker-Bot), [adebrouvier](https://github.com/adebrouvier/expense-tracker-bot), [PersonalExpenseReport](https://github.com/R3D4NG3L/PersonalExpenseReport) | Простые CRUD-боты — как ориентир по минимальному UX ввода. |

**Общие практики, которые подтверждаются везде:**

1. Ввод расхода должен занимать 2–3 тапа или одну строку текста. Всё, что дольше, — не используется.
2. Категории — плоский справочник + быстрые кнопки «последние 6 использованных».
3. Деньги хранятся строками/целыми, не float.
4. Sheets — это то, что нравится людям как *витрина* и *бэкап*, а не как транзакционная БД.

## 2. Google Sheets как хранилище: честная оценка

### Факты (официальные лимиты)

- **Квоты API v4:** 300 read/min на проект, 60 read/min на пользователя; 300 write/min на проект, 60 write/min
  на пользователя. Дневного лимита нет. При превышении — `429`, нужен экспоненциальный бэкофф.
- **Размер:** до 10 млн ячеек на всю книгу (все вкладки суммарно).
- **Латентность:** один вызов API — обычно 200–800 мс, иногда до 2 с.

### Что это значит для нас

Объём — вообще не проблема. 2 человека × ~300 транзакций в месяц × 12 колонок ≈ 43 тыс. ячеек в год.
До лимита в 10M — сотни лет.

Квоты — тоже не проблема при аккуратной работе (батчи), но **60 запросов/мин на пользователя** легко выжечь,
если каждый рендер экрана Mini App ходит в Sheets.

### Настоящие проблемы Sheets как primary storage

| Проблема | Последствие |
|---|---|
| Нет транзакций и атомарных read-modify-write | Два человека одновременно правят баланс → потерянное обновление. `values.append` относительно безопасен, а вот «прочитать баланс → записать баланс» — нет. |
| Нет индексов и выборок | «Покажи траты за июль по категориям» = выкачать весь лист и фильтровать в памяти, либо тянуть Visualization API с SQL-подобным синтаксисом (хрупко). |
| Латентность в критическом пути UI | Открытие Mini App = 0.5–2 с ожидания вместо мгновенного. На мобильном интернете хуже. |
| Внешняя зависимость | Протух service account, отвалился Google, кончилась квота → приложение не работает вообще. |
| Схема ломается руками | Человек вставил строку/переименовал колонку — парсинг падает. |
| Нет миграций | Добавить поле = ручная операция над всеми вкладками. |

### Вывод и рекомендация

**Не делать Sheets источником правды. Сделать SQLite источником правды, а Sheets — двусторонним зеркалом.**

```
Telegram Mini App ──HTTP──> FastAPI ──> SQLite (source of truth, WAL)
                                          │
                                          ├─ outbox ──> фоновый воркер ──batch──> Google Sheets
                                          └─ <──── импорт правок из Sheets (по кнопке / по расписанию)
```

Что получаем:
- UI отвечает за 5–20 мс, а не за секунду.
- Транзакции, целостность, миграции (Alembic), нормальная аналитика на SQL.
- Sheets остаётся ровно тем, ради чего он нужен: открыл с телефона/ноута, посмотрел, построил свой график,
  поправил опечатку, скачал бэкап. Работает, даже если наш сервер лежит.
- API Google перестаёт быть в критическом пути: упал — записи копятся в outbox, поднялся — долились.

Альтернатива «только Sheets» (без БД) имеет ровно один плюс — на один компонент меньше. За это платим
скоростью, гонками и невозможностью нормально считать аналитику. Для 2 пользователей это выживет, но
«расширяемым» такое приложение не будет. Считаю это плохим разменом.

### Сложность интеграции: низкая

Конкретно:
1. Google Cloud проект → включить Sheets API → создать **service account** → скачать JSON-ключ.
2. Расшарить таблицу на e-mail сервис-аккаунта с правами Editor. Всё, OAuth-флоу и refresh-токены не нужны —
   это самый простой из возможных путей.
3. Библиотека: официальный `google-api-python-client` или `gspread`. **Важно:** у `gspread` сейчас проблемы с
   поддержкой (мейнтейнеры ищут преемников), поэтому берём официальный клиент — он скучнее, но живее.
4. Пишем **батчами**: `spreadsheets.values.append` для новых строк, `values.batchUpdate` для изменений.
   Один вызов на пачку, а не на строку.
5. Ретраи с экспоненциальным бэкоффом на `429`/`5xx`.

Реально это ~200–300 строк кода в одном модуле `sheets_sync.py`. День работы.

### Как выглядит таблица

Вкладки:
- `transactions` — плоский лог, одна строка = одна операция. Первая колонка — `id` (ULID), она же ключ
  синхронизации. Плюс `updated_at` и `row_hash` для детекта ручных правок.
- `accounts`, `categories`, `users` — справочники.
- `dashboard` — только формулы (QUERY/PIVOT), генерируется один раз, приложением не трогается.
  Здесь человек развлекается как хочет.

## 3. Стек

### Бэкенд: Python 3.12

| Компонент | Выбор | Почему |
|---|---|---|
| Web | **FastAPI + uvicorn** | Валидация через pydantic v2 из коробки, async, OpenAPI бесплатно. |
| Бот | **aiogram 3** | Самый зрелый асинхронный фреймворк, webhook монтируется прямо в FastAPI → **один процесс, один контейнер**. |
| БД | **SQLite (WAL) + SQLAlchemy 2.0** | Ноль отдельных сервисов, ноль лишней RAM. Postgres на 2 пользователей — это +150 МБ памяти ни за что. Схема на SQLAlchemy → переезд на Postgres потом = смена URL. |
| Миграции | **Alembic** | С первого коммита, иначе через месяц будет больно. |
| Планировщик | **APScheduler** in-process | Синк в Sheets, дайджесты. Без Celery/Redis. |
| Google | **google-api-python-client + google-auth** | См. выше. |

Почему Python, а не Node (grammY + Hono + Drizzle): Node дал бы ~70 МБ RAM против ~150 МБ и один язык на всём
проекте. Но на горизонте — аналитика между месяцами, LLM-дампы, возможно OCR чеков и импорт выписок, и там
питоновская экосистема сильно удобнее. 80 МБ разницы на VPS с 1 ГБ — это не та экономия, ради которой стоит
терять удобство. Если для тебя важнее TypeScript везде — вариант на grammY тоже рабочий, скажи, и я переиграю.

### Фронтенд: React 18 + Vite + TypeScript

- Доступ к Telegram — через собственную обёртку `src/telegram.ts` над официальным
  `telegram-web-app.js` (~60 строк: `initData`, тема, haptics). От `@telegram-apps/sdk-react`
  отказались при реализации: нам нужны четыре вызова, а SDK ломает API между мажорными
  версиями и тянет лишний вес. Если понадобятся `MainButton`, `CloudStorage` и прочее —
  вернуться к SDK можно, обёртка изолирует это в одном файле.
- **@telegram-apps/telegram-ui** или просто CSS на нативных переменных темы (`--tg-theme-bg-color` и т.д.).
  Никаких MUI/Ant — они утащат 300+ КБ в бандл.
- **TanStack Query** — кэш, оптимистичные апдейты (расход появляется в списке мгновенно, до ответа сервера).
- Сборка в статику, отдаётся Caddy. Бандл целимся держать < 150 КБ gzip.

### Инфраструктура

```
docker compose:
  app    — python:3.12-slim, uvicorn (FastAPI + aiogram webhook), ~150 МБ RAM
  caddy  — статика фронта + reverse proxy + автоматический Let's Encrypt, ~15 МБ RAM
volumes:
  ./data — sqlite + креды
```

Итого ~200 МБ RAM. Спокойно живёт на 1 vCPU / 1 ГБ. Mini App **обязательно требует HTTPS** и домен —
Caddy закрывает это в 3 строчки конфига.

Локальная разработка: Mini App нельзя открыть по `http://localhost` внутри Telegram, поэтому нужен туннель
(`cloudflared tunnel --url http://localhost:8000`) и второй тестовый бот в BotFather.

### Авторизация

1. Фронт шлёт `initData` в заголовке `Authorization: tma <initData>`.
2. Бэк валидирует HMAC-SHA256 (secret = HMAC(`WebAppData`, bot_token)) и проверяет `auth_date` на свежесть
   (окно 24 ч).
3. **Whitelist по `telegram_user_id`** в env — приложение приватное, на двоих. Это самая важная строчка
   безопасности во всём проекте.
4. Дальше выдаём свой короткий JWT на сессию, чтобы не гонять HMAC на каждый запрос.

## 4. Модель данных (эскиз к этапу 2)

Принципы: деньги — целые в минорных единицах (копейки), soft delete, `updated_at` у всего (нужен для синка),
внешние ID для идемпотентности, справочники отдельно от фактов.

```python
class User:          id, tg_id, display_name, created_at
class Account:       id, name, kind(cash|card|savings|shared), currency, is_shared, archived
class Category:      id, name, kind(expense|income), parent_id, icon, sort, archived
class Transaction:   id(ULID), occurred_at, type(expense|income|transfer),
                     amount_minor:int, currency,
                     account_id, counter_account_id,   # counter_* только для transfer
                     category_id, author_id, note, tags,
                     created_at, updated_at, deleted_at,
                     source(app|bot|sheet|import), external_id
class TxSplit:       id, tx_id, user_id, share_minor   # кто сколько должен — «общий счёт»
class SyncOutbox:    id, entity, entity_id, op, payload, attempts, created_at
```

`TxSplit` — это ключ к «синхронизации общего счёта»: каждая операция знает, кто заплатил и как делится, из чего
считается «кто кому должен» и делается settle-up одной кнопкой. Если это не нужно — таблица просто не
заполняется, флаг `is_shared` у счёта решает базовый кейс.

Расширяемость закладывается тремя вещами: Alembic с первого дня, `source`/`external_id` (чтобы позже приехали
импорт выписок и OCR чеков), и слой репозиториев между хендлерами и SQLAlchemy.

## 5. Что предлагаю добавить сверх твоего списка

Отсортировано по отношению «польза / трудозатраты»:

1. **Ввод одной строкой из чата.** `500 продукты пятёрочка` → бот парсит сумму, категорию, заметку и отвечает
   карточкой с кнопками «изменить категорию / удалить». Это то, чем реально пользуются каждый день.
2. **Правила автокатегоризации** — regex/подстрока по заметке → категория. Дёшево, покрывает 70% ввода.
   LLM-догадка как fallback — позже.
3. **Settle-up между двумя** — «Норм должен X» с кнопкой «погасить», создающей transfer.
4. **Регулярные платежи** (подписки, аренда) — шаблоны + автосоздание по расписанию.
5. **Бюджеты по категориям** с уведомлением в чат при 80%/100%.
6. **Еженедельный дайджест** в личку: топ-5 категорий, дельта к прошлой неделе.
7. **Фото чека → черновик транзакции** (LLM/OCR). Дороже остального, но эффектно.
8. **MCP-сервер над БД** — вместо «дампа для LLM» дать нейросети инструмент, который сам ходит в данные
   запросами. Тогда анализ не ограничен размером дампа. Дамп при этом тоже оставляем — как компактный
   агрегат (месяц × категория × пользователь + топ-мерчанты), а не как выгрузку всех строк.
9. **Мультивалютность** с курсом на дату операции — если есть поездки/валютные траты. Дешевле заложить поле
   `currency` сразу (уже заложено), чем добавлять потом.

## 6. План по этапам

**Этап 0 (сейчас):** зафиксировать стек и роль Sheets. → этот документ.

**Этап 1 — скелет:**
- монорепо `backend/` + `frontend/`, `docker-compose.yml`, `Caddyfile`, `.env.example`
- FastAPI с `/api/health` + смонтированный aiogram-webhook, бот отвечает на `/start` кнопкой Mini App
- фронт: одна страница, показывает валидированного пользователя из `initData`
- SQLite + Alembic (пустая начальная миграция), Dockerfile multi-stage
- поднимается локально одной командой и на VPS одной командой

**Этап 2 — модель данных:** сущности выше, миграции, репозитории, сиды справочников, тесты на репозитории.

**Этап 3 — базовый функционал:** добавление расхода/пополнения (Mini App + быстрый ввод из чата),
CRUD категорий, список и итоги за период с фильтрами, общий счёт и балансы, синк в Sheets (outbox + воркер)
и импорт правок из Sheets.

**Этап 4 — аналитика и LLM:** сравнение месяцев по категориям и пользователям, графики, LLM-дамп/MCP,
бюджеты, дайджест.
